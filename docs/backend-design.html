Custodian · MVP backend · design draft for review

Backend design and database architecture

A first draft of how the MVP backend could be put together: the components, how each major use case travels from input to output, and how the database would be laid out. This design is the main output so far. Written to be discussed and changed before real implementation starts.

draft 0.1 · 19 September 2026 · Yahya Mateen · status: for review · implementation not started beyond exploratory checks

1 · What the backend has to do

The MVP is a web app where a person connects one or more mailboxes and Custodian reads, sorts and labels the mail, shows what needs attention, and lets the person act on it. The backend owns everything except the screens.

RequirementWhere it comes from
AccountsSign up, sign in, reset. A session reaches an account, never a mailbox on its own (UC-01, UC-02).
MailboxesConnect a mailbox by app password or provider sign-in; disconnect cleanly (UC-04 to UC-13). Target providers: Gmail (tested), Yahoo, Zoho and iCloud (standard IMAP, expected to work, not yet tried), Outlook (needs a Microsoft app registration and sign-in flow, not yet tried).
Always readingNew mail is noticed within seconds and passed through the pipeline without anyone at a keyboard.
FeaturesThe 50 use cases: today's list, requests and promises, the pile, brands, unsubscribe, storage, spam rescue, reminders, rules, people, threads, search, digest, voice, calendar.
SafetyNothing irreversible without the person seeing the exact wording and saying yes. Nothing is ever deleted. Credentials never in plain text. Model calls never see real names.
SeparationOne customer's mail can never be read by a query meant for another customer.

2 · Components

Solid lines are calls. Dashed: the worker reads each mailbox's app password from the vault; the API writes it there once at connect time. The API and the worker never call each other; they meet only in the database.

Each lane reads left to right: what comes in, which components touch it and in what order, what comes out. Red boxes are the gate; nothing to their right happens without the person's yes.

5 · How requests travel

5.1 · Sign in and connect a mailbox

The password never goes to the log, never goes to the database in the clear, and is only stored after the mail server accepted it. If the server refuses, the person gets the provider's real reason, not a generic error.

5.2 · One pass of the worker

for each connected mailbox (own connection, own store) new = mailbox.new_since(bookmark) ← highest UID (IMAP) or history id (Gmail) if new: for each message: save envelope → pipeline → labels applied → decision recorded else: scan 3 older messages ← backlog only when nothing new arrived once an hour: scan recent mail for requests and promises check whether unsubscribed senders actually stopped send the digest if it is due and there is something to say sleep 20 s

The worker holds no approval, so it can only do reversible things. Everything it does is written to the actions table with how to undo it, before the call is made.

5.3 · An irreversible action

The token is bound to the wording. If the pile changed between preview and confirm, the wording changes, the token no longer fits, and the request is refused. This applies to clearing, unsubscribing, sending, batch forwarding and creating rules. The same gate exists in the terminal version; the API reuses it rather than adding a second one.

6 · Database architecture

Two layers. A small shared layer that knows who the customers are, and one private schema per account that holds everything about that person's mail.

Why one schema per account

OptionHow it worksWhy not / why yes
account_id columnAll customers in the same tables, every query filtered by account_id.Common and fast to set up. One forgotten WHERE exposes another customer's mail. Rejected for now because the privacy promise is the product.
One schema per account proposedSame tables, one namespace per account. The connection is pointed at the account's schema once, from the session.Separation is structural, not a habit. Every existing script keeps its SQL unchanged. Fine to several thousand accounts; would need revisiting far beyond that.
One database per accountFull physical separation.Strongest separation, but connection counts and migrations become a problem early. Too heavy for an MVP.

Rules the schema enforces

  • No message body column. Bodies live in a separate table, kept for a short window and trimmed on start. Headers are enough for everything except drafting.
  • Credentials in their own table, encrypted before they arrive. A dump of any other table never contains one.
  • Every action row carries its undo and is written before the call is made. If the process dies in between, the record errs toward "it may have happened".
  • Nothing is ever deleted from a mailbox. Trash is a move; the provider keeps it recoverable.
  • Message-ID is the key, not the provider's id, so the same mail seen through IMAP and Gmail API is one row.

9 · Decisions

9.1 · Decided, technical

  1. One schema per account for customer separation (section 6).
  2. Per-user mailbox connections in the API. Each request opens the caller's own mailbox from the vault, cached per account. The single shared connection in the exploratory code is a prototype shortcut and will not survive.
  3. Push over polling where the provider supports it (Gmail push, IMAP IDLE), polling only as the fallback. This is what keeps the 1,000 and 10,000 user rows in section 8 down.
  4. Chat model chosen by measurement. A fixed 50-sentence test set first; the smallest model that passes wins. Parked until then.
  5. Local models stay local. The classifier and name spotter run on our servers; the name spotter never leaves, since its job is to find the private parts.

10 · What exists right now, plainly

This design is drawn from the proof of concept and from exploratory backend work done to check it holds together, on one laptop against one test mailbox: the shared tables were applied to a hosted Postgres, a copy of the test mailbox was loaded, and the sign-in and a few of the routes were tried. That code is exploratory, not production quality, and is expected to be reshaped or replaced after this review. Nothing is deployed, nothing has been used by more than one person, and nothing has been pushed to a shared repository.
