Node D — the actions

What the Agent Does

Every action the agent can take, and the one thing that decides how much permission it needs: how far the effect travels. Something that only moves an email inside your own mailbox is nothing like something that sends a message in your name.

How far does the effect travel?

Who actually performs each action?

Always the same answer: our own code. No model ever touches a mailbox. The model produces a small answer; our code turns that answer into one instruction.

The one rule underneath all of it

Look at the last column. The actions with no undo are exactly the actions that need approval every time. The actions that undo instantly need approval once.

That's the entire design principle: permission is set by how hard the mistake would be to fix — not by how clever the agent is, and not by how confident the model happens to be.

And why Tier 4 pays for itself twice

Refusing to build delete isn't only about safety. Asking Google for full-mailbox access — which includes permanent delete — pushes an app into a much heavier annual security assessment. By never asking for it, we stay in the cheaper tier.

The safest choice and the cheapest choice turned out to be the same choice. That usually means the design is right.

The actual mechanism for every action

Named calls and named tools, so every claim here can be checked. Door 1 is Gmail, Outlook and the other full-API providers; Door 2 is the older IMAP mailboxes.

Tier 0 — on our server. Nothing in the mailbox changes.

ActionWhat performs itThe actual call
read The mailbox API Gmail: users.messages.get — with format=metadata for envelope only, format=full to open it
Graph: GET /me/messages/{id}
IMAP: FETCH n (ENVELOPE) or FETCH n (BODY[])
parse email (stdlib) or flanker Turns raw text into sender, subject, headers, body, attachments. Handles MIME, encodings, nested parts.
classify Our header rules → ModernBERT + SetFit Rules check List-Unsubscribe, Precedence, sender patterns. Unresolved cases go to the model.
extract deadline / amount duckling → dateparser → model duckling returns candidates with probabilities; below 0.80 it escalates. Every answer is verified against the original text before use.
detect sensitive Our own rules Sender-domain list (banks, health, government) plus a pattern test on the subject — code|OTP|verification near a 4–8 digit number. Runs before everything else so nothing can open it by accident.
build sender memory Our database A query over history we already stored: how many of this sender's messages did you reply to? No AI, no mailbox call.

Tier 4 — never built

There is no delete function anywhere in our code. Not disabled, not commented out — it does not exist. And we never requested the permission, so the provider would refuse the instruction even if a bug produced one. Two independent barriers.

What you can now claim

Every action above is a named API call or a named library. None of it is speculative, and none of it requires anything to be invented.

The three genuine engineering problems are named too, rather than glossed over: snooze doesn't exist as an API and must be built; replies need the right threading headers or they break conversations; and on IMAP mailboxes the Sent copy must be filed by us or it goes missing.
