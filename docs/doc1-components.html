Every component of the system:
what it is, what it does, and why it is that way

OCloud Solutions  ·  state of the proof of concept on 11 September 2026  ·  written from the code as it runs, not from the plan

Custodian is an agent that runs a person's inbox for them. It reads what arrives, decides what needs the person, handles the rest without asking, and never sends anything as them without an exact typed yes. This document walks every part of it and, for each part, answers the same six questions: what is it, what does it do, how does it do it, why is it there, why is it built that way, and why not some other way.

2doors into a mailbox — Gmail API, IMAP
17pipeline stages, models only at four of them
4models — three ours, one rented
9database tables, none holding whole mail
16ways a person meets it (scripts + one web page)

The one idea underneath everything

The more damage an action could cause, the more permission it needs. And the cheapest thing that can decide correctly is the thing that decides.

Those two sentences explain most of the choices below. Rules run before models because rules are free, instant and cannot be argued with. Models are used only where reading meaning is genuinely required. Anything irreversible — sending, forwarding, unsubscribing, trashing — stops at a gate that is written in our own code, below the models, where nothing inside an email can reach it.

A  ·  The shape

Five layers. Mail enters through a door, walks a fixed pipeline, leaves traces in a small database, and a person meets the result through one of several surfaces. Models sit at the leaves of the pipeline, never at its trunk.

Neither is named above this line. │ └──────────────────────────────────────────────────────────────────┘ │ Envelope (sender, subject, date, what the sender declared) ▼ ┌─ C · THE PIPELINE ───────────────────────────────────────────────┐ │ 3 sensitive? → 4 header facts → 2 strip → 5 forms → 7 dates │ │ → 16 commitment → 8 READ (model) → 6 route → 9 needs a reply? │ │ → 10 redact → 19 voice → 11 WRITE (model) → 12 restore │ │ → 13 APPROVE (typed yes) → 14 act (15 unsubscribe, 17 quick) │ └──────────────────────────────────────────────────────────────────┘ │ decisions, actions, reminders, corrections ▼ ┌─ D · THE MEMORY ─────────────────────────────────────────────────┐ │ store.py → mailbox.db: headers of everything, text of 30 days │ └──────────────────────────────────────────────────────────────────┘ │ ▼ ┌─ F · THE SURFACES ───────────────────────────────────────────────┐ │ web.py (browser) chat.py (sentences) agent.py / watch.py │ │ brief · waiting · inbox · mailbox · correct · history · my_data │ └──────────────────────────────────────────────────────────────────┘ E · THE MODELS sit inside stages 8, 9, 10, 11 only: our classifier (8) · our reply gate (9) · our name finder (10) · Gemini (11, and 8 when unsure)

Why five layers and not two

The obvious build is one script that logs into Gmail, sends everything to a large model, and does what the model says. That was rejected for three reasons that each appear again below: it costs money on every email, it sends every email to an outside company, and in published testing every one of 1,404 email agents built that way was hijacked by instructions hidden in email text. The layers exist so that cost, privacy and safety are properties of the structure, not promises made in a prompt.

The order the stages actually run in

The stage numbers are the order of the original design. The order they execute in is different, on purpose. Stage 3 (is this sensitive?) runs before stage 2 (open and strip the body), because stage 2 opens the message and stage 3 exists to decide whether it may be opened at all. Stage 16 (commitments) runs straight after stage 7 (dates) and before stage 9 (needs a reply?), because a meeting reminder is needed whether or not the email needs answering. Stage 6 (the router) reports after stage 8 because it is stage 8 that decides whether to escalate. Each of these is explained at its stage.

B  ·  The doors

A connector is a thin adapter between one kind of mailbox and the rest of the system. There are two today. Nothing above them knows which one is in use.

B1 · The connector interface — connectors/base.py

What it is
A contract: the list of questions every mailbox adapter must be able to answer, and a data shape called an Envelope that every adapter must produce.
What it does
Defines account_email, list_ids, fetch_envelopes, fetch_raw, apply_label, archive, mark_read, trash, and a set of capability flags: supports_push, supports_labels, supports_categories, supports_threads, supports_send, supports_server_search.
How
An Envelope carries only what can be known from headers: sender, subject, date, size, unread, which account it arrived at, whether the sender declared itself bulk or auto-submitted, the unsubscribe headers, and the threading headers. It has no body field, so an envelope-only scan cannot accidentally read a message.
Why it is there
So the pipeline is written once. The rule is ask a connector what it can do, never who it is: code says if conn.supports_push, never if conn.name == "gmail". A third kind of mailbox is then one new file.
Why this way
The capability flags are not decoration. Some differences cannot be hidden — a mailbox that cannot push must be polled, and that is a different code path. Declaring the difference lets the caller choose the path honestly instead of failing later.
Why not otherwise
Hiding every difference behind one identical interface would force the weakest mailbox's behaviour on all of them. Exposing the provider's name would let provider-specific code leak upward, and the second provider would become a rewrite.

B2 · The Gmail API door — connectors/gmail.py

What it is
The adapter for Google's official Gmail API, authenticated with OAuth.
What it does
Everything: lists, fetches headers in parallel (six worker threads, each with its own client because Google's client is not thread-safe), fetches bodies, applies and removes labels, archives, trashes, sends, drafts, forwards, rescues from spam, and asks Gmail what changed since bookmark X through history.list — one quota unit per poll instead of a full re-list.
How
Two OAuth scopes and deliberately not a third: gmail.modify (read, label, archive, trash — not permanent delete) and gmail.send. The full-access scope that permits messages.delete is never requested. Not asking is stronger than promising not to.
Why it is there
It is the richest door: instant push is possible, labels and threads are native, and label removals the user makes in Gmail come back as events (the UC-29 correction feed).
Why this way
Headers are requested by name (From, To, Cc, Subject, Date, List-Unsubscribe, List-Unsubscribe-Post, List-Id, Precedence, Message-ID, In-Reply-To, References, Auto-Submitted) — everything the pipeline needs, nothing more. Fewer bytes, less exposure.
The cost
Google requires a paid annual security audit (CASA, roughly $540–3,000 a year) before an app using the OAuth sign-in screen can serve more than 100 users, and tokens expire every seven days until then. That is a billing rule, not a technical limit, and it is why the second door exists.

B3 · The IMAP door — connectors/imap.py

What it is
The adapter for IMAP, the protocol every mail server on earth speaks, authenticated with an app password. On Gmail it is much more than plain IMAP.
What it does
At connect time it asks the server CAPABILITY. If the answer contains X-GM-EXT-1, the server speaks Gmail's dialect, and three flags flip to true: real labels (X-GM-LABELS), real thread ids (X-GM-THRID), and the whole Gmail search language (X-GM-RAW) including category:primary. It reads headers in batches of 100 per command, reads bodies with BODY.PEEK so nothing is marked read, applies and removes labels, archives (a move to All Mail), trashes, rescues from spam with a single atomic MOVE, polls for new mail by highest UID, and sends over SMTP with the same app password.
How
Every command is a UID command. imaplib's plain fetch, search, store and copy use sequence numbers — a message's position today, which shifts when anything above it moves. A stored position reused tomorrow names a different email, silently. UIDs are fixed for the life of the message.
Why it is there
No audit, no fee, no approval wait, no 100-user cap, no expiring tokens. Measured on a real mailbox: 45 of 47 audited capabilities work, the Primary tab is reachable (1,748 messages), and a real message was sent in 4.9 seconds. The two genuine gaps are server push and snooze.
Why this way
Capabilities are detected, never assumed from the hostname. Plug in a 1998 IMAP server and the Gmail flags stay false, the pipeline still runs, and only the extras are missing. Sending lives here too because the app password that opens imap.gmail.com also opens smtp.gmail.com — "IMAP cannot send" is true about the protocol and wrong about the product.
What the tests changed
Seven defects in this file were found only by running it against a live server: label application that was silently archiving the message; sequence numbers stored as ids; a label parser that dropped any label without a space; a spam-folder lookup that never found Gmail's; missing Gmail folder names; folder creation with an unquoted name (every label with a space failed to exist); and archive that answered OK and did nothing. Each fix is documented in the file beside the code it changed, with the run that found it saved in test_runs/.

B4 · The factory — connect.py

What it is
The one file that chooses a door.
What it does
open_mailbox() returns a Gmail connector or an IMAP connector. --imap forces IMAP, --api forces the API, and with neither it uses IMAP when an app password is set and no OAuth token exists. It also holds the HOSTS map (which IMAP server serves which domain) and three helpers every surface shares for reopening a stored message: live_id, fetch_verified, looks_imap_uid.
Why it is there
So that no other file contains the words "gmail" or "imap". That is what makes "only the connection changes" true rather than claimed — and it was proved: the same email through both doors produced identical output, with only the connector line differing.
Why the helpers live here
A stored provider_id belongs to the door that saved it. An API id means nothing to IMAP; an old IMAP id can name a different message. fetch_verified looks the message up by Message-ID when it has to and then checks the Message-ID inside what came back matches what was stored, refusing otherwise. One copy of that rule, used by the web page, the mailbox view, the brief and the backlog scanner, because five copies would be five chances to disagree.

C  ·  The pipeline

One message at a time, through a fixed sequence. Each stage either attaches facts, exits early, or hands the message on. The rule for the whole pipeline: a rule may route mail; it may never discard it.

Stage 1 · Connect rules

What: the door, from Part B. Does: hands the pipeline an Envelope and says what it can do. Why first: the capability flags decide code paths downstream (poll or push; labels or folders). Why not named: the pipeline prints push=, labels=, never the provider.

Stage 3 · The sensitive gate rules  stage03_sensitive.py

What / does
Decides whether a message may be opened at all, seeing only the sender and subject. If it is sensitive, the pipeline stops here: the body is never fetched, not for a summary, not for a cache, not for anything. The person is told "a message from X arrived, not opened" and nothing more.
How
Four sources, not one list. Domain suffixes that cover whole categories at once (.gov .gov.uk .gc.ca .gouv.qc.ca .mil .bank .insurance .nhs.uk); a seed list of 27 bank, tax and payment domains; sender local-parts that are security channels (otp, 2fa, mfa, verification…); subject patterns for password changes, sign-in alerts, verification codes and a six-digit code in the subject; security subdomains (accounts., security., auth., login., id.) whoever the provider is; and the user's own marks, read fresh from user_sensitive.json on every call.
Why third
Any later and something would already have opened the email before deciding it should not be opened. The ordering is the entire safety property, so the function signature enforces it: there is no parameter for a body.
Why rules, not a model
We want certainty, not a probability, and a model would have to read the very thing we have decided not to read.
Why not a single list
A finite list of banks will always miss one. Suffix rules and channel patterns cover categories; the user's marks cover their own bank; the list is only the seed. Real misses found in testing (“Your Instagram password has been changed”, “New Steam Account Email Verification”) were closed by widening the subject patterns to cover confirmations of a change, not only requests to make one.

Stage 4 · Header facts rules  stage04_headers.py

What / does
Reads what the sender declared about its own mail and turns it into facts: machine-generated (Precedence: bulk), has an unsubscribe header, one-click unsubscribe (RFC 8058), is a reply, is an auto-reply (Auto-Submitted), and whether our provider's authentication stamp passed.
The one exit
engagement_exit: if this person has received at least eight messages from a sender and opened none, the message leaves the pipeline. That is a fact about the person's behaviour, not a guess about the sender.
Why facts and not verdicts
"Machine-generated" is a fact. "Junk" is not — bank statements, flight bookings, invoices and password resets are all machine-generated, and a shop's sale email is noise to one person and the point of the mailbox to another. This stage attaches facts; the decision belongs to stage 9.
Why the authentication check is careful
Only the topmost Authentication-Results header, and only if our own provider stamped it, is trusted. Every header below it was written by whoever sent the mail. Parsing that header without checking who stamped it is an exploitable bug, not a style question.
What testing added
Three headers, not one. Checking only Precedence: bulk let bounces (which set Auto-Submitted) and marketing platforms (which set List-Unsubscribe but not bulk) through as if a person had written them. A person's mail client has never once added a List-Unsubscribe header.

Stage 2 · Parse and strip rules  stage02_strip.py

What / does
Now, and only now, the body is fetched. MIME is taken apart, HTML is turned into text, and the quoted previous conversation and the signature are cut away, keeping only the new words.
How
selectolax for HTML (a C-backed parser, far faster than BeautifulSoup on marketing mail) and email-reply-parser for the quoted history.
Why
It is the single biggest cost saving in the system. Published measurement on 938 real emails put the reduction at about 85%, median 966 tokens down to 124. Measured here: one real message went from 156,130 raw bytes to 5,399 characters. Every model downstream reads the short version.
Why after 3 and 4
Because it opens the message, and stages 3 and 4 decide whether to.

Stage 5 · Forms and layouts rules  stage05_forms.py

What / does
Two mechanisms sharing a stage. Half one: the answer arrived attached — a calendar invite (.ics) carries the exact time, place and attendees; an Apple Wallet pass (.pkpass, a ZIP with JSON inside) carries flight, gate and seat; some invoice PDFs carry the whole invoice as embedded XML (Factur-X / ZUGFeRD). We open the file and read the fields; nothing is interpreted. Half two: a layout fingerprint — your electricity bill looks identical every month, so after a few of them the shape is recorded and no model is ever needed for that sender again.
Why no AI
These are data, not prose. A model reading a calendar invite can only be as right as the file, and can be wrong. Reading the file directly cannot be wrong.
Why it matters downstream
UC-23: a category label (flight, invoice, meeting) is applied only when the sender declared it through one of these files, never from text the model guessed at. A flight label on a message we merely guessed was about a flight is worse than no label — the Owner stops trusting the folder.

Stage 7 · Find dates rules  stage07_dates.py

What / does
Finds phrases in the text that refer to a time, resolves them to a real date, and notes whether a deadline cue (by, before, due, no later than…) sits near each.
How
Three jobs, three tools: find the phrases with dateparser plus our own patterns for relative phrases it misses ("next week", "end of month"); pick which one is the real deadline with a model (stage 11's helper); calculate the date with Python, never a model.
Why never a model for arithmetic
On temporal arithmetic BERT-base scores 25.9 and RoBERTa-large 29.1 against a random baseline of 35.4 — worse than guessing. A model may read that a sentence refers to a time; code works out which time.
What testing added
dateparser is very loose. On real mail it returned "dil" and "bla" from an Urdu song lyric and "150, 41 Comments" from a LinkedIn post as dates, and set reminders for them. A candidate must now look like a date — contain a number, a month, a weekday or a relative word — and a bare number is not a date.

Stage 16 · Commitments rules  stage16_commitments.py

What / does
Turns a date into a reminder that fires. Classifies the kind (meeting, appointment, bill, application, renewal, deadline) and warns by type: two hours before a meeting, a day before an appointment, three days before a bill, six weeks before a passport renewal.
Why it runs here, off stage 7
"Your meeting is tomorrow at 3" needs no reply — stage 9 correctly says so — and it is exactly the message a person most needs surfaced. Reminders were once computed inside the drafting path, so they only happened for mail that needed answering. Reply and remember are different jobs.
Why no approval
A reminder is reversible; the worst case is a notification the user dismisses. The gate is spent where it is needed.
Why an attachment wins
An .ics file is the sender stating the time in a machine-readable field; a phrase in a sentence is us inferring it. When both exist the declared one wins — and it is the only source allowed for machine-sent mail, because "80% off today" from a marketing sender once produced a reminder due at 13:11 that fired at 13:16.
Why the keyword order is load-bearing
"Passport renewal" was classed as a bill (three-day warning) because bill's list contained "renew" and was checked first. Specific kinds are checked before general ones.
Learning
BR-88: repeatedly dismissing a warning as too early moves it later; acting on it at once moves it earlier. Stored as a correction, not a model weight, so it takes effect on the next reminder.

Stage 8 · Read it model  local_classifier.py · model.py

What / does
The only place anything reads an email to understand it. It answers one question: does this need a response from the person? Our own model answers first; a rented model answers only when ours is unsure.
How
An XLM-RoBERTa-base classifier (278M parameters, multilingual) fine-tuned on this mailbox, loaded once and held in memory, about 110 ms per email on a laptop CPU, text never leaving the machine. Topic ("work", "money or bills", "account or security"…) is a coarse bucket, so rules do it — free and instant, no second model to keep in step.
Why this and not a large model for everything
Gemini takes 1–2 seconds, costs money per email, and the text leaves. Ours is free and private. The two sit together through stage 6.
Honest state
Trained on 199 examples from one mailbox. Strong on the classes with data, weak on the ones with two examples each. It proves the component works end to end; it is not yet good enough to ship. What improves it is more labelled data and the correction loop.

Stage 6 · The router rules  model.py

What / does
Decides whether to trust our model's answer or escalate to the rented one. The rule: escalate when our model's confidence is below 0.65. Never on subject matter, never on category.
Why confidence and not category
A category rule ("send all legal mail to the big model") would send the same mail every time regardless of whether the small model could handle it. Confidence sends only what the small model genuinely cannot do, which is the only spend that buys anything.
What it caught on its first run
Our model called a song lyric a request at 0.53; the router escalated; Gemini answered "no response needed" at 0.90.
Degrades, does not stop
With no Gemini key it keeps our answer and says so. With Gemini failing it keeps our answer and says so.

Stage 9 · Needs a reply? model  stage09_gate.py

What / does
Answers "will this person actually act on this?" without re-reading the email. It combines stage 8's meaning with history: have they replied to this sender before, opened them before, is it addressed only to them, is it in a thread, is the sender verified, is it business hours, is it a request.
How
Hand-set weights give a probability. If a trained model exists for this mailbox (LightGBM, 17 features, trained on what this person opened) its score is averaged with the hand-set one, not substituted. The verdict is "needs a reply" when the probability is at least 0.45 and stage 8 said it was a request. Every verdict carries its reasons, written at the moment it is made.
Why history beats words
Measured on real enterprise mail, feature groups on their own scored: history with the sender 0.692, what the email was understood to mean 0.595, timing 0.540, the raw words 0.511 — chance is 0.500. Everything combined: 0.721. So stage 8 reads once; stage 9 decides using what it understood plus history.
Why blended, not replaced
The trained model's AUC is 0.684, below the published 0.72–0.79 ceiling, and it learned "opened", which is a slightly different question from "replied". Two mediocre estimates that disagree for different reasons beat either alone, and a bad training run can never swing a decision on its own.
The bug this stage taught
It compared stage 8's label against a vocabulary written for an older four-way classifier. When stage 8 became binary its label was not in the set, so "is a request" was always false, so nothing was ever "needs a reply" — while printing a plausible probability every time. Two components each doing what they were written to do, joined by a string comparison nobody re-checked.

Stage 10 · Redact model  stage10_redact.py · local_pii.py

What / does
The only door out of the building. Names, email addresses, card numbers, IBANs, national identifiers (CNIC, NI, SSN, SIN), phone numbers and URLs are replaced with placeholders before any text reaches an outside model. The text is also cut to the least that will do the job (3,000 characters).
How
Patterns first, then the model. Structured identifiers have checkable structure, so a regular expression gets them essentially right every time; the model once called a credit card an SSN. Names have no structure, so only the model can find them. Patterns claim what they are certain about; the model takes what is left. The mapping from placeholder to real value is held in memory for the life of the request and never written to disk.
Why one door
With one exit we can show what left; with several we can only hope.
The honest limit
On a benchmark of real documents, a model self-reporting 98.82 F1 scored 0.27, and nothing tested beat a non-expert human at 0.77. So the claim we can defend is "we strip identifiers, we minimise what crosses, and we contract for zero retention" — not "names are removed".

Stage 19 · Your voice rules  stage19_voice.py · learn_voice.py

What / does
Learns how this person writes, from their Sent folder only. Two things are stored: a profile (how they open, how they sign off, how long they write, how formal) made by plain counting, and examples — their own past replies, each stored as a vector so the four or five closest to the current situation can be handed to the writing model as samples.
Why not a model trained on the user
Nothing about them is baked into any model's weights. Deleting the account removes it completely — there is no model to unlearn.
Why no separate vector database
Thousands of vectors per user and a few searches a day is not a job for a second system. POC: TF-IDF vectors as blobs in SQLite, compared in numpy. Production: the same vectors in Postgres with pgvector. "No separate vector database" is not "no vectors".

Stage 11 · Write it model  model.py · prompts.md

What / does
Drafts a reply from the redacted text, the profile and the examples. It never sends. It is the only paid step in the pipeline.
How
Gemini (gemini-flash-latest, with three fallbacks when the free tier is busy), using the draft_reply prompt from prompts.md. Every prompt the system ever gives a model is in that one file, editable without a developer, because wording is a product decision.
Why rented here and not owned
Reading is a classification, which a small model does well. Writing in a person's voice is generation, which small models do badly. Production decides between Claude and Gemini by blind comparison on real drafts, not by benchmarks.

Stage 12 · Names back rules

The placeholders are swapped back for the real values, on our side, before the person ever sees the draft. If any placeholder cannot be resolved the draft is discarded rather than shown half-restored.

Stage 13 · Approve rules  stage13_approval.py

What / does
The most important code in the system. Nothing irreversible — send, forward, unsubscribe, trash — happens without an exact typed yes. Reversible things — label, archive, mark read, snooze, remind, rescue from spam, draft — happen freely and are logged with how to undo them.
How
The draft is hashed. The yes is bound to that hash, so editing the draft voids the earlier yes. The yes must be an exact match against a short list ("yes", "send it", "haan", "ji", "theek hai"…), never a substring — "don't send it" contains "send it". Approval expires after 24 hours. The default, for anything ambiguous, is that nothing happens.
Why in code and not in a prompt
In published testing all 1,404 real email agents tested were hijacked, most within about two attempts, and the attack works by telling the model it need not ask. A model's manners are a behaviour, and behaviours can be argued with. This code never reads the email, so nothing inside an email can reach it.
Why a draft needs no approval
UC-25: a draft in the Owner's own Drafts folder cannot leave without them pressing send in their own mail app. The approval is structural rather than procedural, which is stronger.

Stage 14 · Act rules  stage13_approval.execute()

One connector call per decision. The audit row is written before the call, with how to reverse it — if the process dies in between, we have a record of an action that may not have happened, which is the correct direction to fail. A send with no recipient is refused before anyone is asked to approve it, because asking someone to approve a send that cannot work trains them to click yes on things that do nothing. The send line itself is the only line in the project that puts mail into the world, and it is reachable only through the check above.

Stage 15 · Unsubscribe rules  stage15_unsubscribe.py

Irreversible, and that is not obvious. You cannot un-unsubscribe. So it sits with send behind a typed yes. Two mechanisms exist and only one is safe: RFC 8058 one-click (a single HTTPS POST to a header the sender advertised) is done; a link in the body (a page with a button somewhere, possibly a login, a survey, a tracking beacon that fires on open) is refused and handed to the person instead. Refusing to act is a real answer.

Stage 17 · Quick replies rules  stage17_quick.py

UC-26. A surprising share of replies are one word — "Yes", "Thanks", "Received". Sending those through a language model is paying for prose where none is wanted. A fixed list of eight answers, suggested by what the message asked, at most three at a time, no model, no cost. The tap is the approval (BR-96), and the exact text is shown before it goes.

Why there is no stage 18. The numbering is the design's; stages were added as use cases arrived (15, 16, 17, 19) and one number was never assigned. Renumbering would break every reference in the documents, the meeting notes and the code comments for no gain.

D  ·  The memory

One SQLite file, mailbox.db, behind one module, store.py. The design in one sentence: headers of everything, ever; the text of the last 30 days, important only; everything older fetched live when opened.

Why SQLite and not Postgres

One file, zero setup, in the standard library, and every query in the POC is a few thousand rows. Production is Postgres — the same schema, with the vector blobs becoming a pgvector column. Nothing in the queries depends on SQLite; the swap is the connection string and a migration.

Why Message-ID is the key, and provider_id is a handle

The Message-ID header is written by the sender's mail system and is the only identifier that means the same email in Gmail, Outlook, JMAP and IMAP. The provider's own id is a handle that belongs to one door — and on IMAP it belongs to one folder. The same message CC'd to two of the Owner's accounts is one row when shown and two copies when acted on, matched on Message-ID (BR-99).

E  ·  The models

Why the models are at the leaves

Every stage that can be rules is rules: sensitivity, header facts, stripping, forms, date arithmetic, reminders, the approval gate, unsubscribe, quick replies. The models are spent on exactly three things a rule cannot do — read what a person meant, weigh many weak signals about whether they will act, find a name in free text — and one thing a small model does badly, writing in someone's voice. That is why the pipeline is deterministic with models at the leaves, and why a wrong model answer is always caught or overridden by a rule (a machine-sent flash sale scored "needs a reply" at stage 9 and was still shown as machine mail, because stage 4's fact wins).

How training data was got without a labelling budget

The gate: the mailbox already knows the answers (opened, replied), so 30,000 messages are 30,000 examples the moment the scan finishes. The classifier: distillation — a large model labels ten emails per request (batch_label.py), a small one learns from those labels, and the small one inherits the large one's mistakes until real corrections improve it. Then careful hand labels (dump_for_labelling.py → labels.txt → apply_labels.py), because the classifier is shared across every user and is labelled once, ever. The name finder: a public dataset already marked up.

What is planned and not done: shrinking

shrink_model.py converts the classifier to ONNX at 8 bits: from 1.1 GB PyTorch to roughly 280 MB, measured elsewhere at about 14× faster on CPU, and production never installs PyTorch. Written; not yet run.

H  ·  The rules that cut across everything

Eight rules that no single component owns and every component obeys.

1Instruction vs dataText the user types is an instruction and goes to user_input.py. Text inside an email is data and goes to stages 2, 8, 10, 11. They never share a code path, which is why an email cannot issue a command.
2The gate is codeNothing irreversible without an exact typed yes bound to a hash of the exact text, checked by Python that never reads the email. Not a prompt, not a model's manners.
3One door outEverything that reaches an outside model passes through stage 10. Redaction mapping lives in memory only.
4No body columnThe messages table cannot hold mail. The bodies table is the bounded, auto-trimmed, 30-day exception, and it excludes sensitive mail by construction.
5Capability, not identityAsk a connector what it can do. No file outside connect.py and connectors/ names a provider.
6Message-ID is the keyThe only identifier that means the same email on every door and every day. Provider ids are handles that belong to one door, and are verified on reopen.
7Rules before models; models at the leavesA rule that fires is free, instant and predictable. Models are spent only where nothing cheaper can decide. A rule's fact always wins over a model's guess.
8Move, never deleteThe system never permanently deletes and never asks for the permission that could. Every action is logged with its "before", so undo is by definition rather than by effort. A decision that is not written down did not happen.

And the working method that produced the code

Every non-obvious choice is written beside the code it explains, marked ⚠️, in the words a reviewer would need: what was wrong, how it was found, why the fix is this and not the other. A test that talks to the real server is written before a claim is repeated. When a test finds that the system changed something it should not have, the run is kept, the change is reverted, and the test is made to check its own claim afterwards.
